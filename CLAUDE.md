# fib-bot — контекст проекта для Claude Code

Этот файл читается автоматически при каждом запуске `claude` в этой папке.
Он написан потому, что Claude Code на сервере НЕ видит ни проект claude.ai
"Междусабойчик" (где лежат регламент, бриф, архитектура, список инструментов),
ни память предыдущих сессий. Всё, что здесь написано — это перенесённый контекст,
а не догадки.

## Что это за система

Телеграм-бот, который скринит активы на сетапы по Фибоначчи и присылает алерт,
когда цена уходит в глубокую коррекцию (0.618 и глубже).

**Это боевая система, а не песочница.** Сигналы получают три реальных человека
(Леонид, Сергей, Pavel), которые по ним принимают торговые решения. Всё, что
ломает бота, ломает его для них.

Работает автономно с 24 августа 2026, сейчас **пятью ветками** через cron
root-пользователя (две исходные + две добавлены 5-6 сентября 2026 + одна добавлена
20 сентября 2026; шестая, крипто-ветка, была включена 20 сентября и выключена
23 сентября 2026 — см. ниже):

| Что | Как часто | Файл запуска | Память дедупликации | Реальная отправка |
|---|---|---|---|---|
| Точечный watch по IBM | каждые 15 минут (`*/15 * * * *`) | `run_live.sh` → `orchestrator.py` | `output/alert_state.json` | да, при коррекции 0.618+ |
| Скринер по 14 инструментам | раз в час (`0 * * * *`) | `run_screener.sh` → `screener.py` | `output/screener_state.json` | да, при коррекции 0.618+ |
| Аналитик-дайджест по 15 инструментам (IBM + 14) | раз в час, минута 5 (`5 * * * *`) | `run_analyst_report.sh` → `analyst_report.py` | нет (вердикт на каждом прогоне для всех, шлёт только когда есть ПОКУПКА/ПРОДАЖА) | да (`ANALYST_REPORT_SEND_REAL=1`), без intraday в кроне (лимиты FMP) |

Первые две ветки — level-watch: шлют алерт только при коррекции 0.618/0.786/1.0,
с памятью (не дублируют один и тот же уровень), и при реальном срабатывании
отправляют **два сообщения**: сначала PNG-график (`sendPhoto`), следом полный
текст. Третья ветка — периодическая сводка "что бот думает сейчас" по всем
инструментам сразу, независимо от level-watch. Четвёртая — новый алгоритм
(`build_dual_direction_fibo`, локальные окна на месячном/недельном ТФ, обе
стороны), работает ВДОБАВОК к первым трём, их не заменяет и не трогает
(регламент, раздел 25 — пороги и методика дневного/глобального уровня не
менялись). Первый реальный прогон после включения отправит алерты по всем
кандидатам, которые были видны в dry run на момент переключения (память
`mtf_state.json` до этого не велась) — это ожидаемо, не дубль.

**Дыры в данных Yahoo (найдено 24 сентября 2026).** Yahoo то отдаёт, то
обнуляет (null OHLC) обычный торговый день: за 22.09.2026 пустая свеча
пришла у 89 из 233 инструментов широкого скринера. `load_yahoo_daily()`
такие строки пропускает, цепочка локальных сеток на истории с дырой
откатывается назад, и старая дедупликация 22-24 сентября повторно разослала
события по AMC, SOXX, SPXL, XLK, CSCO. Исправлено в
`broad_screener.py::_new_local_grid_events` (отметка по каждой глобальной
сетке только растёт, откаты не шлются и не запоминаются; подробности в
докстринге). Сама дыра в данных НЕ закрыта: алерт может посчитаться по
истории без одного дня. `crypto_screener.py` (выключен) держит копию
старой дедупликации — если ветку вернут, её надо поправить так же.
Уровневый watch (`should_send_level_watch`) от этого бага не страдал.
С того же дня `broad_screener.py` пишет в лог статус доставки по каждому
получателю (как `mtf_screener.py`).

## Архитектура: агенты

Поток: `Data → Fibo → Price-Behavior → Verification → (Intraday, Context) → Dispatch`

| Модуль | Роль |
|---|---|
| `agents/data_agent.py` | Котировки FMP: `load_fmp_daily()` (дневные), `load_fmp_intraday()` (1H/4H) |
| `agents/fibo_agent.py` | Точки по теням, сетка уровней. Два независимых метода поиска экстремумов |
| `agents/price_behavior_agent.py` | Тест / пробой / закрепление / ретест / ложный пробой + подтверждение объёмом |
| `agents/verification_agent.py` | Чек-лист + сверка двух методов построения структуры (НЕ блокирует отправку) |
| `agents/intraday_agent.py` | Подтверждение на 1H/4H (раздел 7.3 регламента) |
| `agents/context_agent.py` | Макро-календарь FMP (ФРС, CPI, NFP, ВВП, ОПЕК+) — пометка поверх алерта |
| `agents/chart_agent.py` | PNG-график, тёмная тема, matplotlib |
| `agents/dispatch_agent.py` | Формат сообщения (раздел 24) + отправка в Telegram. С 20-21 сентября алерт облегчён до 3 строк (заголовок с ценой · направление с границами · риск; см. докстринг `_format_alert_compact`); полная форма раздела 24 осталась только в нейтральной сводке (превью/консоль) |
| `agents/risk_agent.py` | Риск-блок алерта (21 сентября): R:R, расстояние до стопа, объём при риске 1% депозита, флаги "стоп внутри шума"/"очень широкий стоп". Только арифметика по геометрии, не прогноз |
| `agents/edge_stats.py` | Измеренные базовые частоты исходов сигнала (21 сентября) — СГЕНЕРИРОВАН из `research/`, руками не править. **В алерты не выводится** (строку убрали по решению Леонида 21 сентября); модуль и тесты остались. Пересчёт — см. раздел "Исследование методики" ниже |
| `agents/local_grid_agent.py` | Локальные сетки по PDF-спецификации Леонида (двусвечное подтверждение), используется `broad_screener.py` и `crypto_screener.py` |
| `recipients.py` | Единый список получателей (Леонид/Сергей/Pavel) — править ТОЛЬКО здесь |

Отдельно: `backtest.py` — walk-forward симуляция (малая выборка, см. раздел "Исследование методики"), `screener.py` — цикл по 14 инструментам, `research/` — воспроизводимое исследование методики на ~650 инструментах.

## Методология — правила, которые нельзя менять молча

Полный регламент живёт в проекте claude.ai (`claude/fibonacci-reglament.md`) и
пока не перенесён сюда. Ключевое, что закодировано и подтверждено Леонидом:

- **Конвенция точка1/точка2 перевёрнута относительно многих платформ.**
  Точка 1 = 100% = начало движения. Точка 2 = 0% = конец движения.
  Для ВОСХОДЯЩЕГО движения точка 1 = LOW, точка 2 = HIGH.
  Из этого следует: **инвалидация = цена точки 1, цель = цена точки 2.**
  Это подтверждено 31 августа, не пересматривать без прямого указания Леонида.
- **Точки берутся по теням** (не по телам), подтверждение точки — минимум
  5 баров слева.
- **Раздел 7.1:** глобальный экстремум ищется только внутри переданного окна;
  правило — "самый старый непробитый экстремум".
- **Раздел 7.3** (окна для внутридневного подтверждения — рабочий дефолт Claude,
  НЕ число от команды): 1H — потолок 15 торговых дней, 4H — 60 торговых дней.
  Если команда Леонида пришлёт свой список баров по ТФ — он имеет приоритет
  и заменяет эти числа.
- **Порог алерта: 0.618 / 0.786 / 1.0.** Уровни 0.236/0.382 — не повод для алерта.
- **Цвет 0.786 — зелёный, закреплён регламентом** (раздел 16). Остальные цвета
  графика — временная рабочая палитра, не финал.
- **Раздел 2 регламента — главное правило проекта:** не имитировать результат.
  Если данных не хватает — честно сказать, что не хватает, а не подставить
  правдоподобное число. Это относится и к коду (`insufficient_data` вместо
  выдуманного исхода в бэктесте), и к ответам в чате.
- **Раздел 25:** при конфликте методик нельзя молча выбрать вариант — надо
  спросить Леонида.

## Правила работы на этом сервере

**Никогда:**
- Не выводить содержимое `.env` в консоль, в файлы, в git, в чат. Там реальные
  `TELEGRAM_BOT_TOKEN` и `MARKET_DATA_API_KEY`. Секреты читаются только через
  `source .env` внутри shell-обёрток.
- Не запускать ничего, что реально шлёт в Telegram, без явного разрешения в
  этом конкретном разговоре. Скрипты `preview_*.py` рассылают по-настоящему
  всем троим — это не тесты.
- Не трогать `crontab` без явной просьбы. Сейчас там ровно пять строк
  (см. таблицу выше), проверяется через `crontab -l`. (Изменение crontab
  автоматический классификатор Claude Code блокирует — Леонид вносит его сам.)
- Не удалять и не переписывать `output/alert_state.json`,
  `output/screener_state.json` и `output/mtf_state.json` — это память
  level-watch между запусками. Их порча = поток дублирующих алертов у трёх
  человек. (`alert_state.json` создаётся лениво при первом реальном
  срабатывании 0.618 — его отсутствие на диске само по себе не проблема.)

**Всегда:**
- Перед любым изменением кода агентов — запустить ВСЕ шесть наборов тестов
  (ожидаемые числа — в блоке "Как проверить" ниже). После изменения — запустить
  снова. Падение регрессии = откат, а не "поправим потом".
- Продакшен-путь проверять живым прогоном, а не только тестами: раньше каждый
  деплой подтверждался реальным выводом сервера.
- Изменения в код агентов вносить точечно. Файлы на сервере — источник истины;
  GitHub-репозиторий (`github.com/leonid14022003-eng/fib-bot`) отстал с 24 августа
  и НЕ является актуальной копией.

## Исследование методики (21 сентября 2026) — что измерено, что НЕ подтвердилось

Воспроизводимо: `research/` (см. докстринги скриптов; `research_validate.py`
доказывает, что быстрый движок побитово совпадает с боевым
`backtest.simulate_symbol` — 271 сигнал, 56 инструментов). Данные: ~650
инструментов (599 акций, 9 индексов/товаров, 38 крипто), до 10 лет дневных
свечей Yahoo/Binance. Каждая оценка — против КОНТРОЛЯ (случайные входы на тех
же инструментах с той же геометрией), доверительные интервалы — блочный
бутстрэп по месяцам и по инструментам, деление времени на обучение (<2022) и
проверку (>=2022).

**Результаты (метод как в проде: экстремумы окна 5 лет, откат 0.618/0.786):**
- Покупка отката (восходящая структура): +1R раньше стопа за 60 дней у 26% сигналов
  против 15% у случайного входа; за 120 дней 38% против 27%. Знак эффекта
  совпадает в обеих половинах истории. Умеренное, но не громкое преимущество.
- Продажа отскока (нисходящая структура): **на уровне случайного входа или хуже**
  (за 250 дней +1R раньше стопа 28% против 33% случайного). Преимущества нет.
- Крипта: выборка мала (n≈90), преимущество не подтверждено.
- Цель (точка 2) достигается редко: за 60/120/250 дней — ~2/8/20% у покупок отката.
  Номинальный R:R до точки 2 — это геометрия масштаба ВСЕГО движения (месяцы-годы),
  не ближайший отскок.
- Средний результат по всем сигналам ≈ +0.06R (E1, как в `backtest.py`) / +0.08R
  (цель = точка 2) — малая величина; после учёта коррелированности сигналов
  внутри одного месяца доверительный интервал едва отделён от нуля.

**Что было проверено и ОТВЕРГНУТО данными (не внедрять повторно без новых данных):**
- Сетка на "последнем значимом свинге" вместо глобального экстремума окна —
  проверено ТРИ способами (второй проход 21 сентября, `research_backtest_recompute.py`,
  `research_local_grid_study.py`, `research_lg_robust.py`), результат в разделе ниже:
  зигзаг на фракталах (3/5 ATR) — избыток ≈0; `find_global_grid()` из
  `local_grid_agent.py` — это НЕ свинг, а тот же ATH/ATL окна (см. ниже); цепочка
  локальных сеток — без заметного улучшения абсолютного результата.
- Фильтры-confluence как условия отправки (тренд SMA200, свеча-подтверждение
  разворота, объём отката, режим рынка по ^GSPC, свежесть отката, размер
  импульса): знак эффекта МЕНЯЕТСЯ между обучением и проверкой — устойчивого
  улучшения нет. В бот НЕ добавлены (это внедрение шума).

**Второй проход: "последний свинг" через `local_grid_agent.py` (21 сентября, вечер).**
Вопрос Леонида: пересчитать `backtest.py`, подставив вместо "старейшего непробитого
экстремума" сетку на последнем значимом свинге. Ключевое уточнение: `find_global_grid()`
в `local_grid_agent.py` — буквальный ATH/ATL окна, то есть НЕ свинг; "свинг" в этом модуле
— цепочка локальных сеток (`run_local_grid_chain`). Проверены оба, плюс зигзаг.
- **Буквальный `backtest.py`** на 646 инструментах (подмена `extremes_fn`, метрика
  `backtest.py`): текущий метод 3099 сигналов, +0.02R, win 51% (LONG +0.19R, SHORT -0.19R).
  С `find_global_grid()`: те же 3099 сигналов с теми же исходами + 1310 ЛИШНИХ, все на
  самом начале истории/окна (медиана — 32-й бар), они убыточнее (-0.09R против +0.04R).
  То есть правило "5 свечей слева" — защита от структур, приколотых к искусственной
  границе окна (в контролируемом прогоне 100% лишних сигналов `find_global_grid`
  начинаются в первых 5 барах скользящего окна, у общих с боевым методом — 0%).
- Зигзаг "последний свинг" в метрике `backtest.py`: 86 865 сигналов, -0.84R (-0.09R после
  отбрасывания уровня 1.0 и ограничения убытка -3R) — но сравнивать сырой avgR НЕЛЬЗЯ

- **Цепочка локальных сеток** (L1 любая стадия, L2 только "зафиксирована"), реалистичный

- **Открытый вопрос для Леонида (раздел 25 регламента — конфликт методик):** живые ветки

- **"Убрать потолок 5 лет, брать всю историю"** (проверено 21 сентября вечером,

  возможно (потолок — просто `months_back=60` / `limit=1000`; FMP Starter и Yahoo отдают всю
  историю: Tesla с 2010, IBM с 1962; Binance — до 1500 свечей за запрос, нужна пагинация).
  Но данные против: окно 5 лет / 10 лет / вся история → сигналов 2638 / 1703 / 420; медианный

  шкала (в регламенте/PDF — линейная). Плюс скорость: `find_oldest_unbroken_extremes` на 16 000
  свечей ≈ 2.7 с на инструмент локально (на 1 vCPU сервера в 2-3 раза дольше) — часовой прогон
  ~250 инструментов вырастет с секунд до десятков минут. В бота НЕ внедрено.

**Оговорки, которые нужно помнить (в `agents/edge_stats.py` они тоже записаны):**
выборка "выжившая" (сегодняшние члены индексов) — результаты покупок откатов
завышены, контроль убирает это лишь частично; прошлые частоты не гарантируют
будущих; уровень 1.0 для глобальной структуры недостижим (цена за точкой 1 сама
становится новым экстремумом окна и структура перестраивается).

для восходящих структур (позже подсказка убрана вместе с облегчением алерта).
